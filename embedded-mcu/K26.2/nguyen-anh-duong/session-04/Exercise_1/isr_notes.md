1. A flag shared by an ISR and a task must be declared `volatile` because the ISR can change it at any time. Without `volatile`, the compiler may read the flag once and keep using the old value. For example, it may turn `while (!flag)` into a loop that never notices the flag changing, or it may assume that the value in `if (flag)` cannot change by itself. The compiler does not automatically know that an ISR writes the variable, so the ISR write does not stop this optimization. `volatile` tells the compiler to read the real value from memory each time.

2. Calling `ESP_LOGI()` or `vTaskDelay()` inside `button_isr()` is dangerous because the ISR is running in interrupt context. An ISR must not block or wait for the scheduler. `ESP_LOGI()` may use a lock and may do formatted output, which can take too long or wait for another task. `vTaskDelay()` tries to block the current task and use the scheduler, but an ISR is not a normal task. This can cause an assertion, deadlock, watchdog reset, or delayed handling of other interrupts. The ISR should only read the button and notify the task with an ISR-safe function.

3. The queue version is faster in theory. When the ISR sends an event, the task can wake up right away, usually in less than one FreeRTOS tick. With a 100 Hz tick, that is about 10 ms. The flag version checks the flag every `TASK_DELAY_MS`, so its worst-case response is about 25 ms. The queue version also uses less CPU when the button is untouched because the task can sleep in `xQueueReceive(..., portMAX_DELAY)`. 
However, for this assignment, the queue version was easier to get wrong when the button was pressed many times quickly. 
Several press and release events can build up in the queue, events can be delayed, and a small queue can become full. That can make the click and double-click logic behave unexpectedly unless the queue and debounce handling are designed carefully. The flag version was easier for me to use in this small task because it only keeps the current button state, although it can miss very fast changes and uses more CPU while polling.
